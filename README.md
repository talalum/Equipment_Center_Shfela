# מרכז ציוד שפלה — ניהול מלאי

אתר בעברית שמחזיק את תקן המחסן, קולט אוטומטית את מיילי ההנפקה מחשבון Gmail ייעודי,
ומציג במסך אחד **מה התקן ומה חסר עכשיו**.

---

## איך זה עובד

```
מיילי הנפקה ──► חשבון Gmail ייעודי ──IMAP כל 5 דק'──► המערכת ──► לוח מצב
```

1. **התקן והמלאי** מיובאים מקובץ Excel או CSV. נקראות ארבע עמודות:
   `מק"ט`, `שם פריט`, `תקן מאושר` (או `תקן`), ו-`מלאי לאחר הגעת משלוח`
   (או `מלאי עדכני`). ההעלאה לא משנה כלום עד שמאשרים השוואה — ראי
   [ייבוא קובץ התקן](#ייבוא-קובץ-התקן).
2. **כל מייל הנפקה** נקרא מהתיבה, מפורק, וכל שורה משויכת לפריט **לפי המק"ט**.
3. **המלאי מתחיל מלא לפי התקן**, וכל הנפקה יוצרת חוסר עד שהמלאי מחודש.

### הנוסחאות

```
הונפק            = Σ(שורות הנפקה מהמיילים שנקלטו)
מלאי עדכני בארון = תקן − הונפק + Σ(תנועות ידניות)
חסר              = max(0, תקן − מלאי עדכני בארון)
```

`מלאי עדכני בארון` יכול לעלות מעל התקן אם התקבלה אספקה גדולה — זה מותר, ואז `חסר` הוא 0.
הוא גם העמודה היחידה שהתנועות הידניות מזיזות; `הונפק` מדווח על המיילים בלבד.

### שני כללי הזהב

- **מייל לא נספר פעמיים.** הדדופליקציה היא לפי `Message-ID`, וגם הדבקה ידנית של אותו
  טקסט פעמיים לא תשפיע על המלאי.
- **קליטה היא הכל-או-כלום.** מייל עם שורה אחת שלא זוהתה ממתין **כולו** לאישור ידני ולא
  נכנס למלאי. קליטה חלקית יוצרת מלאי שגוי בשקט — וזה בדיוק מה שהמערכת אמורה למנוע.

### מה נחשב מייל הנפקה

הזיהוי הוא לפי המשפט **"ההזמנה שלך מוכנה"** שמופיע בכל מייל הנפקה — ולא לפי שם הנמען.
חלק מההנפקות הן **לכלי ארגוני** ומגיעות בלי שם אחרי "שלום"; הן הנפקות לכל דבר ונספרות
בדיוק כמו כל האחרות.

מייל שזוהה כהנפקה אבל רשימת המוצרים שבו לא נקראה **אינו נזרק** — הוא ממתין במסך
"ממתין לאישור". הנפקה שנעלמת בשקט היא חוסר במלאי שאיש לא יודע עליו, וזה בדיוק מה
שאסור שיקרה. מייל שאינו הנפקה כלל (בלי המשפט ובלי רשימת מוצרים) נשמר כ"לא רלוונטי"
ואינו נוגע במלאי.

## הרצה מקומית

דרוש פייתון 3.10 ומעלה.

**Windows**
```
py -m pip install -r requirements.txt
py -m app.server
```

**Mac / Linux**
```bash
python3 -m pip install -r requirements.txt
python3 -m app.server
```

ואז לפתוח **http://localhost:8000**. לעצירה: `Ctrl+C`.

בהרצה ראשונה המערכת יוצרת את המסד ומייבאת אוטומטית את `data/Inventory_Report.csv` —
בשורת הפקודה תופיע ההודעה `ייבוא ראשוני מקובץ התקן: נוספו 76`.

> **ווינדוס:** לווינדוס אין מסד אזורי זמן משלה, ולכן `ZoneInfo("Asia/Jerusalem")` נכשל
> שם. `requirements.txt` מתקין את חבילת `tzdata` בווינדוס בדיוק בשביל זה. גם אם היא
> חסרה המערכת לא תקרוס — היא תיפול לשעון של המחשב ותרשום אזהרה.

האזהרות על `APP_PASSWORD_HASH` ו-`SESSION_SECRET` בעלייה תקינות ומכוונות בהרצה מקומית;
הן נדרשות רק לפני העלאה לענן.

### עם Docker

```bash
cp .env.example .env    # ולמלא ערכים
docker compose up
```

## איפה הנתונים נשמרים

המערכת עובדת עם שני מנועי מסד, והבחירה ביניהם היא לפי משתנה סביבה אחד:

| `DATABASE_URL` | המנוע | מתי |
|---|---|---|
| ריק | **SQLite** — קובץ מקומי | הרצה מקומית. ברירת המחדל |
| מוגדר | **PostgreSQL** — שרת נפרד | בענן |

הסכימה, השאילתות וההתנהגות זהות בשני המצבים, ואותה חבילת בדיקות רצה מול שניהם.
בהרצה מקומית אין מה להגדיר — הכל עובד כמו קודם.

### במצב SQLite (מקומי)

הכל יושב בקובץ אחד: **`data/warehouse.db`**. הוא נוצר לבד בהרצה הראשונה ומכיל את
רשימת הפריטים, התקן, כל ההנפקות שנקלטו וכל תנועות המלאי.

זהו קובץ רגיל על הדיסק. הוא נשאר שם כשסוגרים את השרת, כשמכבים את המחשב, ולתמיד —
בדיוק כמו מסמך Word.

> ⚠️ **בהורדת גרסה חדשה — הנתונים לא עוברים לבד.**
> ZIP חדש מגיע עם תיקייה חדשה וריקה. כדי לא לאבד את ההיסטוריה, להעתיק מהתיקייה
> הישנה לחדשה שני קבצים:
>
> | קובץ | מה יש בו |
> |---|---|
> | `data/warehouse.db` | כל הנתונים |
> | `.env` | הסיסמה ופרטי התיבה |
>
> אם הקובץ `warehouse.db` לא הועתק, המערכת פשוט תתחיל מחדש מקובץ התקן — שום דבר
> לא נשבר, אבל ההנפקות והתיקונים שנצברו לא יהיו שם.

**גיבוי:** להעתיק את `data/warehouse.db` לכל מקום אחר. זה הכל. לשחזור — להחזיר
אותו למקומו.

### שני כפתורי התנועה בכל שורה

| כפתור | מה הוא עושה |
|---|---|
| **✎ עריכה** | מקלידים את **הכמות שנספרה בפועל**, לא הפרש. המערכת מחשבת את ההפרש בעצמה |
| **⟲ איפוס לתקן** | לחיצה אחת שמחזירה את הפריט בדיוק לתקן. מציג אישור עם לפני → אחרי |

שניהם יוצרים רשומת תנועה. **שום מספר לא נדרס** וההיסטוריה נשמרת במלואה.

> **למה הכפתורים האלה חיוניים:** המערכת מכירה רק מיילי הנפקה, כלומר רק אירועים שמורידים
> מהמלאי. כשמגיעה אספקה מהמחסן המרכזי אף מייל לא מספר על כך למערכת — בלי עדכון ידני
> החוסר יישאר על המסך לנצח.

## הגדרת חשבון ה-Gmail

1. בחשבון ה-Gmail הייעודי: להפעיל **אימות דו-שלבי** (בלעדיו גוגל לא מאפשרת App Password).
2. ליצור **App Password** (16 תווים) עבור "Mail".
3. למלא ב-`.env`:
   ```
   IMAP_USER=the-dedicated-account@gmail.com
   IMAP_PASSWORD=<ה-App Password, בלי רווחים>
   ```
4. לוודא שמיילי ההנפקה באמת מגיעים לתיבה — לשלוח הנפקה אחת ולבדוק.

### מתי נמשכים מיילים

`app.setup` שואל אם למשוך אוטומטית ברקע או רק בלחיצה. ההגדרה נשמרת כ-`POLL_MINUTES`:

| ערך | התנהגות |
|---|---|
| `0` | משיכה **רק** בלחיצה על "⟳ משוך מיילים" באתר |
| `5` | משיכה אוטומטית כל 5 דקות, כל עוד השרת רץ |

בשני המצבים הכפתור באתר עובד, ושום הנפקה לא הולכת לאיבוד: הסריקה מכסה 30 יום
אחורה ולא תלויה בשאלה אם המייל נקרא, ולכן הפעלה אחרי תקופה של חוסר פעילות
משלימה את כל מה שהצטבר.

### מאיזה תאריך נקלטים מיילים

בלוח המצב, מעל טבלת הפריטים, יש שורה מתקפלת: **"קליטת מיילים למלאי"**. אפשר לבחור
בה תאריך ושעה, ומאותו רגע והלאה מייל שקודם לתאריך הזה **נרשם במערכת אך אינו נכנס
למלאי**. ברירת המחדל היא בלי הגבלה בכלל.

למה זה נחוץ: הנפקה שקרתה לפני אותו תאריך כבר מגולמת במה שנמצא על המדף בפועל, ולכן
מייל ישן שנקלט מאוחר יוצר חוסר על ציוד שכבר הוחזר — אותה הנפקה נספרת פעמיים. אם
בוצע איפוס לתקן, השדה מגיע מוכן עם תאריך האיפוס האחרון, שהוא בדיוק הרגע שממנו
העבר הפסיק להיות רלוונטי.

התאריך משפיע בשני מקומות: הסריקה בתיבה מתחילה ממנו (חיסכון בתעבורה בלבד, לפי שעון
ישראל), וההחלטה המחייבת נעשית בקליטה — שם יש חותמת זמן מלאה. הנפקה שממתינה לאישור
וקודמת לתאריך אינה ניתנת לאישור, וההודעה מסבירה שכדי לקלוט אותה בכל זאת צריך להזיז
את התאריך.

### ביטול הספירה של מה שהונפק לפני התאריך

התאריך לעיל מטפל במיילים שעוד יגיעו. להנפקות שכבר נקלטו יש כפתור נפרד באותה שורה:
**"⊘ בטל את הספירה של N ההנפקות שלפני התאריך"**. הוא מופיע רק כשנשמר תאריך ויש מה
לבטל, ומבקש אישור שמפרט בדיוק מה יקרה.

מה הוא עושה: מוציא מהספירה את ההנפקות שקודמות לתאריך, כך שהמלאי של הפריטים שבהן
חוזר לכמות שהייתה לפניהן. **לא נרשמת שום תנועה מפצה** — ההנפקות פשוט מסומנות ביומן
ההנפקות כ"לא נספר", והמייל המקורי נשמר כמו שהוא.

**להחזיר הנפקה לספירה** אפשר דרך "נתח מחדש" ביומן ההנפקות, אבל קודם צריך להזיז את
התאריך: כל עוד התאריך במקומו, ניתוח מחדש מכבד אותו ומחזיר את ההנפקה מיד ל"לא נספר".

למה לא פשוט "איפוס לתקן": איפוס מכריח את הפריט לכמות התקן המדויקת, ולכן מוחק גם
חוסרים מהנפקות **שאחרי** התאריך, שהן אמיתיות וממתינות. הביטול מוציא רק את החלק
שמשויך לעבר, ומשאיר את מה שאחריו כמו שהוא. הוא גם לא מוסיף שורת תנועה לכל פריט,
כך שיומן התנועות נשאר נקי.

**מתי הוא מסרב:** אם נרשמה תנועת מלאי (איפוס או עדכון) לאחר שההנפקות האלה כבר
נכללו בספירה. תנועה כזו שומרת הפרש קבוע שחושב מול מה שהיה קלוט באותו רגע, ולכן
ביטול ההנפקה שמאחוריה היה משאיר זיכוי בלי כיסוי והמלאי היה עולה מעל התקן — זה מה
שקרה בייצור, כשהפלסטרים הציגו 312 מתוך תקן של 320 בזמן שהונפקו 10. במקרה כזה
ההודעה מפנה ל**"עדכון מלאי"**, שמצהיר על הכמות שבאמת נמצאת בארון.

### בדיקת החיבור

```
py -m app.checkmail          (ווינדוס)
python3 -m app.checkmail     (מק/לינוקס)
```

מתחבר, ומדווח מה נמצא בתיבה ואילו מיילים מזוהים כהנפקות. **אינו מסמן מיילים
כנקראו ואינו נוגע במלאי** — אפשר להריץ אותו כמה פעמים שרוצים. אם החיבור נכשל,
הוא מסביר בדיוק למה (סיסמה שגויה / אין רשת / חומת אש) במקום להדפיס שגיאה טכנית.

בלי הפרטים האלה המערכת עובדת רגיל, רק בלי משיכה אוטומטית — דרך מסך ההדבקה.

> **על ה-App Password:** זו סיסמה נפרדת שנותנת גישה לקריאת דואר בלבד, ואפשר לבטל
> אותה בכל רגע בלי לגעת בחשבון. אם היא נחשפה — למחוק אותה ב-
> myaccount.google.com/apppasswords וליצור חדשה. היא נשמרת רק בקובץ `.env`
> המקומי, שאינו נכנס ל-git.

**המערכת לא נוגעת בשום תשתית ארגונית:** אין רישום ב-Azure AD, אין בקשות הרשאה מ-IT,
ואין תלות ב-Exchange.

## ייבוא קובץ התקן

הייבוא נעשה במסך **ניהול פריטים** (`/items`), מקובץ Excel (`.xlsx`) או CSV.

### אילו עמודות נקראות

| בקובץ | לאן נכנס | הערות |
|---|---|---|
| `מק"ט` | המק"ט | המפתח שהכול מתחבר לפיו |
| `שם פריט` | שם הפריט | |
| `תקן מאושר` או `תקן` | עמודת **תקן** | |
| `מלאי לאחר הגעת משלוח` או `מלאי עדכני` | עמודת **מלאי עדכני בארון** | אם שתיהן בקובץ — הראשונה גוברת, כי היא המאוחרת מבין השתיים |

כל שאר העמודות בדוח — `מלאי נוכחי`, `חוסר נטו`, `כמות בהזמנה נוכחית`,
`הגיע בפועל`, `סטטוס והסבר` — **מתעלמות במכוון**. הן תוצאה של חישוב שהמערכת
עושה בעצמה, ולייבא אותן פירושו להחזיק את אותו מספר בשני מקומות שיכולים לסתור.
שימי לב במיוחד ל-`מלאי נוכחי`: זה המלאי *לפני* הגעת המשלוח, כלומר בדיוק המספר
שאסור לייבא.

### ההעלאה לא משנה כלום — עד לאישור

```
העלאת קובץ ──► סריקה בלבד ──► פופאפ השוואה ──► [אישור] ──► המלאי מתעדכן
                                            └─► [ביטול] ──► שום שינוי
```

אחרי ההעלאה נפתח פופאפ שמראה, לכל שורה שמשתנה, מה יש היום מול מה שיהיה:
המלאי בארון (עם ההפרש), התקן, ושינויי שם. פריטים שלא משתנים אינם מוצגים —
רק נספרים. פריטים שקיימים במערכת ואינם בקובץ מוצגים בשמם באזהרה נפרדת:
**הם נשארים בדיוק כפי שהם**, לא בתקן ולא במלאי.

הקובץ הסרוק ממתין בטבלה `pending_imports` ולא בזיכרון, כדי שרענון דף, הפעלה
מחדש של השרת או תהליך שני לא יאבדו אותו באמצע. העלאה חדשה מחליפה את מה שממתין.

### מה קורה באישור

עדכון המלאי נרשם כ**תנועה** לכל פריט, בדיוק כמו ספירת מלאי ידנית, ומופיע ביומן
התנועות עם שם הקובץ כסיבה. פריט שכבר נמצא בכמות הנכונה לא מייצר תנועה ריקה.

ההפרש מחושב **ברגע האישור** ולא ברגע הסריקה — אם בין השניים נקלט מייל הנפקה,
המלאי עדיין ינחת על המספר שכתוב בקובץ. הקובץ מצהיר מה יש בארון, וזה מה שקובע.

ייבוא חוזר מעדכן לפי מק"ט ולא מוחק היסטוריה.

### הייבוא הראשוני בעלייה שונה

בהתקנה חדשה המערכת מייבאת לבד את `data/Inventory_Report.csv` — ושם **עמודת
המלאי לא נקראת**. התקנה חדשה מתחילה מלאה לפי התקן (ראי [שני כללי
הזהב](#שני-כללי-הזהב)); המלאי זז רק כשאדם מעלה קובץ ומאשר את ההשוואה.

## הגדרת סיסמה וחיבור לתיבה

הדרך הפשוטה — פקודה אחת ששואלת שאלות וכותבת הכל לבד:

```
py -m app.setup          (ווינדוס)
python3 -m app.setup     (מק/לינוקס)
```

היא מגדירה סיסמת כניסה, יוצרת מפתח חתימה אקראי, ואם רוצים גם את פרטי תיבת ה-Gmail.
הכל נכתב לקובץ `.env` שנשאר על המחשב בלבד ולא נכנס ל-git.

שאלות הכלי ושאר הפלט בשורת הפקודה הם באנגלית — הממשק עצמו נשאר כמובן בעברית.

אחרי שינוי ב-`.env` צריך להפעיל את השרת מחדש (`Ctrl+C` ואז להריץ שוב).

### הגבלות על העלאת קובץ

בטופס "ייבוא קובץ תקן" שב-`/items` יש שתי הגבלות, ושתיהן נאכפות בשרת:

| הגבלה | ברירת מחדל | איפה נאכפת |
|---|---|---|
| סוג הקובץ | `XLSX` ו-`CSV` | `config.ALLOWED_UPLOAD_TYPES` — הבדיקה לפי סיומת השם, ב-`main.items_import` |
| גודל הקובץ | 8MB | `MAX_UPLOAD_BYTES` (משתנה סביבה) — `web.build_request` |

הפורמט הבינארי הישן `.xls` לא נתמך במכוון: זה פורמט אחר לגמרי, שאי אפשר לקרוא
בלי ספרייה חיצונית. קובץ כזה יש לשמור מחדש מאקסל כ-`.xlsx`.

שתי ההגבלות מוצגות למשתמשת מעל שדה הקובץ, ונקראות מאותו מקום בקוד — כך שמה שכתוב
בממשק הוא בדיוק מה שהשרת אוכף.

קובץ מסוג אחר נדחה בהודעה בעברית וההעלאה לא מתבצעת. קובץ גדול מדי מקבל `413` —
הגוף שלו לא נקרא כלל ולא נחתך, כי CSV חתוך נראה תקין ושורות היו נעלמות בשקט.
התכונה `accept` שבטופס היא רמז לדפדפן בלבד ואי אפשר להסתמך עליה, ולכן הבדיקה
נעשית גם בצד השרת.

להגדלת המגבלה: `MAX_UPLOAD_BYTES=16777216` ב-`.env` (16MB). להוספת סוג קובץ יש
להוסיף שורה ל-`ALLOWED_UPLOAD_TYPES` — הממשק, ה-`accept` והבדיקה מתעדכנים יחד.

### מה כל הגדרה עושה

| משתנה | למה |
|---|---|
| `APP_PASSWORD_HASH` | הסיסמה לכניסה. בלעדיו **האתר פתוח לכל מי שמגיע לכתובת** |
| `SESSION_SECRET` | חותם על עוגיית הכניסה. בלעדיו אפשר לזייף עוגייה ולהיכנס בלי סיסמה |
| `COOKIE_SECURE` | `1` = העוגייה נשלחת רק על HTTPS. **בהרצה מקומית חייב להישאר `0`**, אחרת לא תתאפשר כניסה |

השרת מדפיס אזהרה בעלייה על כל אחד מאלה שחסר. הסיסמה נשמרת כ-PBKDF2-SHA256 בלבד —
לעולם לא כטקסט גלוי, לא בקוד ולא במסד.

להחלפת סיסמה בלבד אפשר גם `python -m app.hashpw`, שמדפיס את השורה להעתקה ידנית.

## פריסה לענן

עובד על כל שירות שמריץ Docker (Render, Railway, Fly.io).

### למה Postgres בענן

שירותי אירוח חינמיים נותנים מערכת קבצים **זמנית**: בכל ריסטארט או דיפלוי הקונטיינר
נבנה מחדש וכל קובץ שנוצר בתוכו נמחק. במצב SQLite זה אומר ש-`warehouse.db` נעלם.

מה שאפשר לשחזר אחרי מחיקה כזו: הפריטים והתקן (מיובאים מחדש מה-CSV) וההנפקות
(נמשכות שוב מ-Gmail). מה ש**אי אפשר** לשחזר: **תנועות המלאי הידניות** — כל ✎ עריכה
וכל ⟲ איפוס. הן קיימות רק במסד, ובלעדיהן החוסרים על המסך שגויים.

כשהנתונים יושבים ב-Postgres הקונטיינר הופך חסר-מצב: אפשר להרוס ולבנות אותו מחדש
בלי לאבד דבר, ואין צורך בדיסק קבוע.

### שלבי הפריסה

**1. לפתוח מסד Postgres** (Neon, Supabase, או כל ספק אחר) ולהעתיק את מחרוזת החיבור:

```
postgresql://user:password@host/dbname?sslmode=require
```

**2. להעביר את הנתונים הקיימים** — מריצים מקומית, כשה-`.env` כבר מכיל את `DATABASE_URL`:

```
py -m app.migrate_to_postgres --dry-run    # רק מראה מה יעבור
py -m app.migrate_to_postgres              # מעביר בפועל
```

הסקריפט קורא מ-SQLite בלבד-קריאה ולעולם לא משנה אותו, משמר את המזהים המקוריים
(ואיתם את הקשרים בין הטבלאות), מסרב לרוץ על יעד שכבר יש בו נתונים, ומאמת ספירות
בסיום. `--replace` מוחק את היעד ומעביר מחדש.

**3. ליצור את השירות** מהריפו. הוא מזהה את ה-`Dockerfile` לבד.

**4. להזין את משתני הסביבה** בפאנל של השירות — לא מעלים קובץ `.env`:

| משתנה | ערך |
|---|---|
| `DATABASE_URL` | מחרוזת החיבור מהשלב הראשון |
| `APP_PASSWORD_HASH` | מתוך ה-`.env` המקומי |
| `SESSION_SECRET` | מתוך ה-`.env` המקומי |
| `COOKIE_SECURE` | `1` |
| `IMAP_USER` · `IMAP_PASSWORD` | אם רוצים משיכת מיילים |
| `POLL_MINUTES` | `0` בשירות שנרדם, אחרת `5` |

> **`POLL_MINUTES=0` בשירותים חינמיים.** הם משהים את השירות אחרי חוסר פעילות, ולכן
> משיכה מתוזמנת ברקע לא אמינה שם. המשיכה תתבצע בלחיצה על **⟲ משוך מיילים**, והיא
> סורקת `LOOKBACK_DAYS` (30 כברירת מחדל) יום אחורה — כך ששום מייל לא מתפספס גם אחרי
> שהאתר היה כבוי שבועיים.

**5. גיבוי:** `pg_dump` מייצא הכל לקובץ אחד. אין נעילה לספק, ואפשר לחזור ל-SQLite
או לעבור ספק בכל רגע.

## אם תבנית המייל תשתנה

הכללים יושבים ב-`config/email_format.yaml` ולא בקוד, כך ששינוי לא דורש דיפלוי:

```yaml
items_start: "המוצרים שהונפקו:"
items_end:   "שם המנפיק:"
item_line:   '^(?P<name>.+?),\s*מק["״]?ט:\s*(?P<sku>[\w\-.]+)\s*[-–—]\s*כמות:\s*(?P<qty>\d+)\s*$'
expected_center: "מרכז ציוד שפלה"
issuance_marker: "ההזמנה שלך מוכנה"
```

`expected_center` מסנן הנפקות של מרכזי ציוד אחרים — הן נשמרות אבל לא נספרות במלאי.
להשאיר ריק כדי לקלוט מכולם.

`issuance_marker` הוא המשפט שקובע שמדובר בהנפקה. הוא נבדק על גוף המייל כולו, כך
שהוא נמצא גם כשהוא מודגש, גם במייל שהועבר, וגם כשתוכנת הדואר שברה אותו לשתי שורות.
אם המשפט בתבנית ישתנה — לעדכן כאן בלבד. להשאיר ריק כדי לחזור לזיהוי לפי
`items_start` בלבד, כלומר לפי רשימת המוצרים.

גוף המייל המקורי נשמר תמיד, ולכן אפשר לנתח מחדש אחרי שיפור הפרסר בלי לאבד מידע.

### הרצה מול Postgres

אותן בדיקות בדיוק רצות גם מול Postgres אמיתי, כדי שההתנהגות לא תתפצל בין המנועים
בלי שנדע:

```bash
docker run -d --name ecs-pg -e POSTGRES_PASSWORD=testpw -e POSTGRES_DB=warehouse \
  -p 55432:5432 postgres:16-alpine

DATABASE_URL_TEST=postgresql://postgres:testpw@localhost:55432/warehouse \
  python -m unittest discover -s tests -t .
```

בלי `DATABASE_URL_TEST` הבדיקות רצות מול SQLite ואינן דורשות שום תשתית.
